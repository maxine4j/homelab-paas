# Management UI

The React management UI is served by the control plane at the cluster's base hostname. It supports platform configuration edits, service secret edits and read-only service/resource inspection. With auth/TLS configured, open `https://{baseDomain}` (including a nonstandard HTTPS port). Envoy requires the existing GitHub allowlisted session before serving the UI or its API; missing or invalid sessions redirect to login, including API requests. OAuth accepts this hostname as a return target. Platform cookies are retained only for the management upstream; workload cookie stripping is unchanged. The authentication hostname still exposes only login and callback routes. Management ingress blocks API paths outside `/api/ui/`.

Without auth/TLS, the base hostname serves HTTP without authentication for trusted local development only. No management hostname, credentials, roles, dependencies, or configuration fields are added. Bootstrap port publication remains operator-owned.

## Views

Service detail begins with the service identity, without a separate “Service” label or “← Services” link. Navigation remains in the topbar breadcrumbs; Refresh and Redeploy belong to the shared service heading below.

Service detail has Overview, Resources, Events and [Secrets](#service-secrets) tabs; resource inspection has Overview, Logs and Events tabs. Event history uses the same identity heading and tab navigation as its parent detail view, with Events selected and no separate back link. History subscribes independently of inspection snapshots: identity and all tabs remain visible while events load, when history is empty or unavailable, and when Git or Docker inspection is unavailable. Service Events uses `#/services/:serviceId/events`; resource Events uses `#/services/:serviceId/resources/:resourceId/events`.

Every event card, including recent-event previews, has a bottom-right “Copy JSON” action. It copies the complete already-redacted event object as formatted JSON, preserving diagnostics and event metadata. Clipboard success and failure have explicit feedback; failed copies can be retried.

In the Resources tab, the entire full-width resource card links to inspection through its keyboard-accessible resource ID link. External ingress links remain independent and open in new tabs. The first row shows resource ID then resource type, with stronger weight and contrast on the ID and resource sync and health at the right. Web cards show only the primary service URL when available, otherwise the resource-specific URL.

- Cluster configuration: a read-only summary at the top presents the effective cluster ID, base domain, HTTP port and HTTPS port, including defaults and environment overrides. An absent HTTPS port shows “Not configured”. The editor below contains only Git, reconciliation and services, grouped by their parent configuration sections. Version, authentication, session and TLS settings are omitted from this page. Services use add/remove forms for the service ID, repository, optional branch and descriptor path rather than raw JSON. Secret inputs show configured status and accept replacements without exposing current values. Environment-managed settings are read-only. Save, reload, pending, validation and conflict states are explicit. Pushed snapshots preserve unsaved drafts. See [management edits](configuration.md#management-edits) for persistence, secret preservation and restart requirements.
- Services: every configured service, its independent sync and health statuses and active revision. Statuses follow the [resource health and sync contract](reconciliation-and-deployments.md#resource-health); live health never derives from persisted deployment phase. The whole card links to service details through a keyboard-accessible link; its independent primary web link opens in a new tab. Cards have three rows: service ID, primary web resource link and both statuses on the first; a single truncated description on the second; left-aligned active commit information on the third. Missing descriptions retain their row for alignment. Hostnames truncate with an ellipsis while keeping the external-link arrow visible. API summaries include optional `description` and `primaryUrl` fields from the latest valid committed descriptor; unavailable descriptors omit both without hiding deployment status. Links describe desired ingress and do not imply readiness. Service detail also shows the next retry time. API summaries additionally include the desired revision and retry count.
- Service detail: service ID, sync and health badges and active/desired revisions share a row on wide screens. At widths up to 1000px the commit panels move together below the service identity; up to 700px they stack vertically, Active above Desired. Side-by-side panels match the taller panel's height. Revision links show seven-character SHAs and open the full GitHub commit in a new tab. Local and unsupported repository sources retain plain short hashes without a link. Commit messages, authors and timestamps remain beneath the hashes. The primary web resource link sits below the service ID. A top tab bar follows the service heading, with Overview, Resources, Events and [Secrets](#service-secrets) links. Overview retains two recent events and compact resource cards; the service descriptor disclosure is omitted. Resources shows one full-width card per resource, with a full-card inspection link, resource sync and health badges, configured Docker image name/tag, and one web ingress link opening in a new tab (the primary service URL when available, otherwise the resource hostname). A globe with “Public ingress” or lock with “Private ingress” reflects the descriptor's explicit ingress policy; unavailable policies and images are identified without inferring private access or using Docker image IDs as names. Empty resources have an explicit empty state. Tabs use ordinary hash links: `#/services/:serviceId` for Overview and `#/services/:serviceId/resources` for Resources, preserving browser history and direct navigation. The API includes `descriptorYaml`, serialized from the same sanitized descriptor as `descriptor`. Resource cards show both badges at the top right. The API requires independent `sync` and `health` on every `UiServiceSummary`, `UiService` and `UiResource`; see [resource health](reconciliation-and-deployments.md#resource-health) for polling and state semantics. Overview resource cards link directly to inspection without an action label; a single Overview resource retains a grid column's width on wide screens. Resources are the union of the latest valid committed descriptor and observed Docker containers. Resources with no containers remain visible; containers belonging to resources absent from the descriptor remain inspectable with type `unknown`.
- Resource inspection: the same resource sync and health badges sit beside the resource ID, matching service status placement on service detail. Individual container lifecycle badges remain in Live state. Inspection includes redacted desired configuration, links to each web resource's hostname and its service alias when primary, live container snapshots (including stopped containers, image identity, revision, running flag and networks), and a container's last 200 timestamped stdout/stderr log lines. Opening Logs selects the first observed container and loads its logs unless the URL explicitly selects another container. The Logs tab has no container dropdown; each container's View logs link in Live state opens its logs directly. Links describe desired ingress and do not imply readiness. Docker multiplexed and plain TTY output are supported. Logs follow live output through the [live subscription protocol](#live-subscriptions); history pagination is unavailable.

Service cards show the active revision hash with its exact commit's message, author name and author date in one compact row. Message and author text truncate as space requires; complete values remain in the markup, and the date retains its complete timestamp. Service-detail revision groups show the full message, author name and timestamp for the active and desired descriptor revisions. Metadata does not appear in resources or events. The service-list API includes optional `activeRevisionMetadata` and `desiredRevisionMetadata` objects; service detail includes optional `activeRevisionMetadata` and `descriptorRevisionMetadata` objects. Each contains `message`, `authorName` and ISO `authoredAt` fields. Metadata uses the shared [Git cache](reconciliation-and-deployments.md#shared-git-cache); missing remote commits are fetched by their exact hash, including active revisions older than the shallow branch checkout. Failed metadata reads are cached until a successful repository refresh, preventing repeated remote requests from management snapshot invalidations. Metadata reads apply known-secret redaction and omit author email addresses. Unavailable metadata leaves the hash visible with “Commit details unavailable”; Git failures do not hide service-list deployment status, and metadata failures do not hide the descriptor or observed resources. An absent revision retains “Not deployed”, “Not observed” or “Unavailable” as appropriate. The primary web resource link on service detail opens in a new tab and displays an external-link arrow.

Views subscribe through WebSocket and receive an initial snapshot followed by pushed replacements when configuration, Git, reconciliation or resource health changes. Production inspection does not poll HTTP. Navigation cancels subscriptions and suppresses stale responses; reconnect resubscribes and replaces snapshots, including log tails. Refresh/retry controls request fresh subscriptions. Empty, loading, unavailable, and missing-item states are explicit. A descriptor read failure preserves observed-resource visibility and marks desired configuration unavailable. Log reads fail closed when the descriptor cannot be loaded for redaction. Snapshots combine independent reads rather than providing a transaction across Git, persisted checkpoints and Docker.

Descriptor literal environment values are available in service-detail API responses and visible in resource configuration, including its YAML disclosure. Secret references remain redacted and their resolved values are never returned. Known platform credentials, embedded URL credentials and command arguments remain redacted, including when credentials appear in literal environment values. Log reads redact exact environment values from the actual container, descriptor environment values and known platform credentials. The API never returns raw Docker inspection payloads or resolved container environment values. Service events expose the explicitly redacted failure diagnostics described below; other API failures retain fixed safe messages. Redaction cannot recognize arbitrary application-generated or transformed secrets: applications must keep credentials out of their logs and failures. Completed HTTP log reads retain bounded response sizes and deadlines; live follows use the stream bounds and cancellation contract below.

The dark layout uses top navigation for Services and Cluster config at all viewport sizes, a flexible resource grid and scrollable configuration panels. Header breadcrumbs follow Services / service ID / resource ID, with links to parent views; event history adds Events beneath the service. Cluster configuration has its own breadcrumb. The footer shows the platform build's seven-character commit hash (full hash on hover) and live connection/reconnection status (or mock snapshots in mock mode). Builds without supplied revision metadata show `Build unknown`. The revision is embedded at build time; see [build metadata](development.md#build-metadata). Phone controls have at least 44px targets. Resource tabs and navigation use ordinary hash links, supporting browser history and direct links without another routing dependency.

Service detail includes a Descriptor tab at `#/services/:serviceId/descriptor`, displaying the API's redacted `descriptorYaml` as selectable, read-only YAML with an explicit unavailable state. Breadcrumbs remain compact. The page heading places the large service name and compact sync and health badges on the left, with Refresh and Redeploy right-aligned on the same row, wrapping on narrow screens. The primary ingress link is always left-aligned on a separate row underneath. Active and Desired revision panels split the following row equally and stack on narrow screens. Event cards place the event name after the severity pill and retain the timestamp at the right. Resource/revision metadata and the right-aligned Copy JSON control share the row below the message and any diagnostics.

One shared service component renders the identity, sync and health, actions, ingress link and both revision panels above the tabs across Overview, Resources, Descriptor, Events and Secrets. Events and Secrets subscribe to service context independently; an unavailable service snapshot does not block their event history or secret controls. Completed heading actions refresh the service context and event history.

Sync and health badges use Argo CD's colour semantics: Healthy and Synced green (`#18BE94`), Progressing blue (`#0DADEA`), Degraded red (`#E96D76`), Missing and OutOfSync yellow (`#F4C030`), and Unknown grey (`#CCD6DD`). Health uses a heart and sync a refresh symbol; accessible labels and tooltips identify the axis, including when both values are Unknown. Both badges appear on service cards and shared service headings, compact and full resource cards, and shared resource headings. They wrap on narrow screens. Container lifecycle badges remain separate in Live state.

## Live subscriptions

`/api/ui/live` accepts same-origin WebSocket upgrades and independently verifies the configured platform session, including direct requests that bypass Envoy. Missing/duplicate cookies are rejected. Open connections recheck session expiry and allowlist revocation every second and before delivery. Envoy enables upgrades only for this management route, retaining authorization and platform cookies; its request and stream idle timeouts are disabled for the route. Heartbeats detect disconnected peers.

Shared runtime-validated messages are `{ type: "subscribe", id, target }` and `{ type: "unsubscribe", id }`. Targets identify cluster, services, service, events, resource or logs using domain IDs. Responses are `{ type: "snapshot", id, target, data }`, fixed safe `{ type: "error", id, message }`, and immediate `{ type: "event", serviceId, event }` notifications for event subscriptions. `UiLiveService` reuses `PaasUiService` aggregation/redaction and coalesces invalidations while a read is running. Immediate events remain visible if their durable append fails. Browser views own their subscriptions and reconnect timers, retry disconnected connections with bounded backoff, and show sign-in guidance after session closure.

Connections allow at most 16 subscriptions, 8 KiB input messages, 16 MiB outgoing queued bytes and 128 concurrent connections. The outgoing budget accommodates a service's latest 200 events with bounded diagnostics; event-history snapshots cover one service per subscription. Malformed, binary or oversized messages and slow clients close. Unsubscribe, navigation, replacement and shutdown release streams and timers. Each mounted browser snapshot/event/log hook owns one connection. HTTP inspection remains available for explicit clients, configuration saves and manual Git refresh.

Logs use Docker Engine `follow=true` with an initial 200-line tail, supporting partial multiplexed frames and split UTF-8. Docker ownership and resource membership are checked before following. The Docker service combines actual container environment values with descriptor values inside the configuration-owned stateful redactor. Possible secret prefixes, multiline values and incomplete URL tokens are withheld across arbitrary chunks; no raw environment values enter public messages. Retained safe output is limited to 200 lines and 131072 characters; individual frames are bounded to 256 KiB and unresolved raw text to 262144 characters, failing closed when exceeded. Confirmed-safe log tails replace the displayed tail, so reconnect does not append duplicate history. Logs auto-scroll; scrolling upward or “Pause follow” freezes the displayed view while bounded live tails continue arriving. “Resume follow” shows the latest tail. Selecting another container resets pause. Configuration changes and service Git refresh restart follows with current authorization/redaction context.

## Manual Git refresh

The services page offers “Refresh all” in the topbar to the right of the breadcrumbs; service detail offers “Refresh” in its shared heading alongside Redeploy. Progress and result feedback appears to the left of the buttons when space permits, wrapping on narrow screens. These actions fetch the configured branch through the shared [Git refresh service](reconciliation-and-deployments.md#shared-git-cache), then run reconciliation from cache. The all-services action fetches repositories concurrently with failure isolation. The single-service action fetches only that service's repository; the subsequent reconciliation pass can inspect every service from cache. Unknown or inherited service IDs fail without side effects.

The control is disabled while running and shows progress, completion or a safe error. Bulk results identify failed service IDs and how many repositories refreshed, including when every fetch fails. A successful Git fetch does not imply successful deployment: inspect the service status and events. Completed requests reload the relevant snapshots and events. There is no separate snapshot refresh button; browser reload reconnects live subscriptions and requests their initial snapshots. Inspection APIs remain available for explicit clients. Navigation cancels waiting and suppresses stale feedback; server work may still finish.

`POST /api/ui/services/refresh` refreshes all configured sources; `POST /api/ui/services/:serviceId/refresh` refreshes one. Both require the existing session when configured, a matching management `Origin`, and `X-Paas-Refresh: 1`, including in unauthenticated local development. Requests have no payload. Cross-origin or missing-intent requests return 403; unknown services return 404 and unavailable operations return a sanitized 503. Success returns the shared `UiGitRefresh` shape `{ results: [{ serviceId, refreshed }] }` with `Cache-Control: no-store`. Bulk partial or complete fetch failure returns 200 with individual false outcomes, provided the reconciliation pass completes; reconciliation failures return 503. `refreshed` describes only the Git fetch. GET/HEAD do not perform these actions.

The router delegates directly to the injected `IGitRefreshService` shared with periodic refresh; it owns no fetch/reconciliation orchestration or separate cache.

### Manual redeploy

Service detail offers “Redeploy” next to “Refresh” in its shared heading on every service tab. Both buttons have equal widths; Refresh uses an information colour and Redeploy a warning colour. Both are disabled during either action, with progress and safe outcome feedback. Redeploy replaces all supported web and worker containers even when their specifications are unchanged, using each resource's configured rollout strategy. Recreate can cause downtime. Volumes and credentials are retained. It uses the committed descriptor available through the shared Git cache; use Refresh first to explicitly fetch remote changes. The mock development preview remains read-only.

`POST /api/ui/services/:serviceId/redeploy` has no payload and requires the configured session, matching management `Origin`, and `X-Paas-Redeploy: 1`. It delegates to the injected reconciler, serializes with periodic reconciliation, and bypasses existing retry backoff for the selected service. Descriptor, capability and secret validation precede workload changes. Success returns 204 only after all resource rollouts complete; unknown services return 404, missing origin/intent returns 403, and failures return a sanitized 503. Responses use `Cache-Control: no-store`; GET/HEAD cannot trigger redeployment. Failures retain normal checkpoints, events and observed-state recovery. Navigation cancels waiting and suppresses stale feedback; server work can still finish. Inspect status before retrying an interrupted request.

## Service secrets

Service detail has a Secrets tab at `#/services/:serviceId/secrets`, alongside Overview, Resources and Events. All service tab views retain this link. Secrets loads independently of Docker inspection and service snapshots, retaining the service heading, tabs and loading/error states. It reads the current committed descriptor and secret-file metadata through an explicit HTTP request; it does not extend the live subscription protocol. Declared secret names each have a password field and configured/missing status. Saved values stay hidden. A checkbox explicitly selects replacements, including valid empty strings; unselected values remain unchanged. Extra variables appear last, labeled Unused, with an add-variable form for future deployments. The mock preview disables editing.

`GET /api/ui/services/:serviceId/secrets` returns `{ revision, variables: [{ name, configured, used }] }`, never saved values or file contents. The opaque revision combines the committed descriptor and secret-file revisions. `PUT` on the same endpoint accepts `{ revision, changes: [{ name, value }] }`. It requires the configured session, matching management `Origin`, `X-Paas-Secrets: 1` and JSON. Unknown/invalid service identities return 404; invalid edits return 400; stale revisions return 409; bodies above 64 KiB return 413; other content types return 415; missing origin/intent returns 403; descriptor/file failures return a safe 503. Both endpoints use `Cache-Control: no-store`. Concurrent API writes are serialized and stale saves cannot overwrite another accepted save. Out-of-band file edits must be atomic; the control plane cannot coordinate their read/write windows.

Reload status retains unsaved drafts, including after conflicts or failures. Successful saves clear submitted drafts. Navigation cancels waiting and suppresses stale results; an accepted write may still finish on the server. The page explains the regular reconciliation/retry schedule. Persistence, format limits and deployment behavior belong to the [secret configuration contract](configuration.md#environment-variables-and-secrets). Secret failure cards link directly to Secrets whenever service identity is available, and retain every missing variable name; JSON copy keeps the original full event.

## Service events

Service detail shows at most two events under “Recent events”, above resources. When more retained events are available, “N more events...” links to `#/services/:serviceId/events`; N counts the remaining events in the fetched history. Event history shows the latest 200 retained events, newest first. Events include timestamp, severity, operation, a safe actionable message, and resource, revision, attempt count and scheduled retry time when available. Retry times describe the schedule when the event was recorded. Event history refreshes independently and remains readable without Git or Docker. Loading, empty and unavailable histories are explicit. Persistence and retention follow [reconciliation events](reconciliation-and-deployments.md#service-events).

Resource Overview also shows two recent events, filtered by an exact `resourceId` match before limiting or counting. Service-wide events without a resource ID and events for other resources are excluded. Its “N more events...” link and Events navigation open `#/services/:serviceId/resources/:resourceId/events`. This page shows every matching event from the service's retained history, independently of descriptor and Docker availability, with links back to the resource and service in the breadcrumbs. Retention is 200 events per service, so resource history is a matching subset, not a separate 200-event history. Both resource views subscribe to the existing service events stream and apply the same filter to immediate notifications and snapshots; navigation releases subscriptions, and disconnected views reconnect with explicit status.

The resource Overview shows one Configuration card followed by one Live state card, using a shared card component and field styling. Logs remain a separate tab; existing `/config` and `/state` resource links both open Overview. Configuration uses compact Image, Deployment strategy, Networking, Environment, Volumes and limit sections within its single card, following the Live state design. The redundant resource type is omitted. Ingress Port and Public appear on the same line. Environment entries use monospace `KEY: value` rows; secret references show `KEY: <secret>` with a contrasting lock badge. Volumes spans the card's full width and includes volume mounts, device mappings and supplementary groups without a separate devices heading. Every mount uses the same CSS grid layout: Host path above Mount path, with long values wrapping inside their value column. Its collapsed Descriptor YAML disclosure shows the complete redacted resource configuration. The API includes `configYaml`, serialized from the same sanitized value as `config`; both are unavailable for observed-only resources. Live state groups all observed containers in its single card and presents container identity, status, revision, image identity, network addresses/aliases and links to container logs, with its full redacted JSON in a collapsed disclosure below the structured view. Both cards retain explicit unavailable and empty states.

All event cards share a first row with the severity pill on the left and timestamp on the right, followed by the message. Failure cards show the actual redacted error message; parseable legacy diagnostics also supply this headline in place of generic reconciliation boilerplate. Cards keep consistent padding and spacing between the heading, message, diagnostics and metadata. Failure events offer an expandable, selectable “Error diagnostics” disclosure with two sections: Stack trace and Context. Each section has a compact heading and padded code block. Stack trace decodes newlines and indentation, retains error chains, aggregate failures and available Docker/provider details, and strips `file:///app/services/paas/` from error paths. Context shows redacted operation/deployment configuration as YAML serialized by the backend's canonical YAML utility. New captures include YAML for immediate delivery; existing parseable JSON contexts are projected to bounded YAML on read without rewriting history. Plain or truncated diagnostics remain selectable fallback text, with unavailable context identified. Text wraps on narrow screens and long diagnostics scroll vertically. Capture, redaction and truncation limits are defined in [reconciliation events](reconciliation-and-deployments.md#service-events); existing events without diagnostics remain readable. Secret failures show the missing names, reason, dotenv line when known, and the host file to edit alongside its container path. Unknown host mappings are marked unavailable with guidance to check the control-plane bind mount; a container path is never labeled as a verified host path. Resolved secret values and secret-file contents remain hidden. See [secret diagnostics](configuration.md#environment-variables-and-secrets). `PaasUiService` reads events through an injected service-event store and verifies that the service is configured before reading its history.

## API and layers

Inspection endpoints are `GET` (also supporting `HEAD`) under `/api/ui`. Responses use `Cache-Control: no-store`; unknown items return 404 and unavailable data 503. The API router independently verifies configured sessions and returns 401 for missing or invalid sessions on requests that reach it directly; external requests through authenticated management ingress redirect to login first. Unsupported methods are rejected. Unknown API paths never fall back to the SPA.

| Endpoint                                                                  | Result                                                                |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `/cluster`                                                                | Cluster identity, redacted configuration, revision and field metadata |
| `/services`                                                               | Configured services with deployment summaries                         |
| `/services/:serviceId`                                                    | Service source, descriptor status/revision and resources              |
| `/services/:serviceId/events`                                             | Latest 200 safe service events, newest first                          |
| `/services/:serviceId/resources/:resourceId`                              | Resource configuration and live container snapshots                   |
| `/services/:serviceId/resources/:resourceId/containers/:containerId/logs` | Bounded, redacted log tail for an owned resource container            |

`PUT /api/ui/cluster/config` accepts `{ revision, changes: [{ path, value }] }` with 1–128 edits. Paths must match editable fields returned by `/cluster`; `services` replaces the service-source mapping as one field. The endpoint requires the existing session when auth is enabled, an `Origin` matching the configured management origin, `X-Paas-Config: 1`, and `Content-Type: application/json`. It rejects malformed requests or invalid edits with 400, cross-origin/missing-header requests with 403, stale revisions with 409, bodies above 64 KiB with 413, and other content types with 415. Persistence failures return a sanitized 503. Success returns a redacted snapshot with the new revision and fields. There is no CORS opt-in. Unauthenticated local development uses the same origin and JSON requirements.

`frontend/paas-ui-router.ts` owns HTTP adaptation and session verification. `PaasUiService` aggregates injected Git, Docker and reconciliation-state interfaces and delegates platform edits and redaction to `PaasConfig`. It shares the same in-memory and disk Git cache with deployment reconciliation. The Git service serializes operations per service and isolates exact-commit fetches from descriptor refs. Docker services enforce cluster/service ownership before reading logs; the UI service additionally verifies resource membership. Shared response types live in `@homelab-paas/shared-contracts`.

Service-source forms select credentials from the repository protocol: HTTPS shows an optional password input for an access token; SSH URLs and SCP-style remotes show an optional absolute private-key path; other sources show neither. Saved tokens show configured status without exposing their values, support replacement/removal, and survive unrelated edits. Changing a repository clears its credential draft. Key paths default in examples to `/etc/homelab-paas/keys/`; arbitrary mounted host paths remain supported. Validation and secret-preservation semantics belong to the [configuration contract](configuration.md#private-git-repositories).

Frontend `pages/` compose reusable `components/`; `hooks/` own navigation and fetching. The Docker image builds and includes the Vite output; the existing static frontend service serves it. Configuration editing does not add deployment controls or expand the [runtime's supported resource capabilities](configuration.md#implemented-deployment-mvp).
