# Management UI

The React management UI is served by the control plane at the cluster's base hostname. It supports platform configuration edits and read-only service/resource inspection. With auth/TLS configured, open `https://{baseDomain}` (including a nonstandard HTTPS port). Envoy requires the existing GitHub allowlisted session before serving the UI or its API; missing or invalid sessions redirect to login, including API requests. OAuth accepts this hostname as a return target. Platform cookies are retained only for the management upstream; workload cookie stripping is unchanged. The authentication hostname still exposes only login and callback routes. Management ingress blocks API paths outside `/api/ui/`.

Without auth/TLS, the base hostname serves HTTP without authentication for trusted local development only. No management hostname, credentials, roles, dependencies, or configuration fields are added. Bootstrap port publication remains operator-owned.

## Views

- Cluster configuration: current effective validated settings, including defaults and environment overrides, with an editor for live settings and service sources. Fields are grouped by their parent sections in the platform configuration. Services use add/remove forms for the service ID, repository, optional branch and descriptor path rather than raw JSON. Secret inputs show configured status and accept replacements without exposing current values. Environment-managed and restart-required settings are read-only. Save, reload, pending, validation and conflict states are explicit. Polling preserves unsaved drafts. See [management edits](configuration.md#management-edits) for persistence, secret preservation and restart requirements.
- Services: every configured service, its persisted phase and active/desired revisions. UI labels map `ready` to healthy (green), `deploying` to deploying (blue), `failed` to unhealthy (red), and unobserved `unknown` to missing (grey). These reflect the last reconciliation checkpoint, not a separate live health probe. Cards show service ID and status on line one, then active revision left-aligned and desired revision right-aligned on line two; the whole card links to service details. Service detail also shows the next retry time. API summaries additionally include the retry count.
- Service detail: a primary web resource link when configured, followed by deployment status, the latest event, resources and the complete redacted parsed service descriptor in a collapsed JSON disclosure. Resource cards link directly to inspection without an action label. Service source is a deep link to the descriptor file at its fetched Git revision on supported GitHub, GitLab and Bitbucket web hosts. Local repositories, unsupported remotes and unavailable revisions show an unavailable-link state. Resources are the union of the latest valid committed descriptor and observed Docker containers. Resources with no containers remain visible; containers belonging to resources absent from the descriptor remain inspectable with type `unknown`.
- Resource inspection: redacted desired configuration, links to each web resource's hostname and its service alias when primary, live container snapshots (including stopped containers, image identity, revision, running flag and networks), and a selectable container's last 200 timestamped stdout/stderr log lines. Opening Logs selects the first observed container and loads its logs unless the URL explicitly selects another container. Links describe desired ingress and do not imply readiness. Docker multiplexed and plain TTY output are supported. There is no log streaming or history pagination.

Snapshots refresh five seconds after each request completes; requests do not overlap within a view. Navigation cancels requests and suppresses stale responses. Refresh/retry controls are available. Empty, loading, unavailable, and missing-item states are explicit. A descriptor read failure preserves observed-resource visibility and marks desired configuration unavailable. Log reads fail closed when the descriptor cannot be loaded for redaction. Snapshots combine independent reads rather than providing a transaction across Git, persisted checkpoints and Docker.

Configuration credentials, literal environment values and command arguments are redacted. Log reads redact exact environment values from the actual container, descriptor environment values and known platform credentials. The API never returns raw Docker inspection payloads, environment values, infrastructure errors or arbitrary persisted error text. Redaction cannot recognize arbitrary application-generated or transformed secrets: applications must keep credentials out of their logs. Docker response sizes and deadlines remain bounded by the existing transport; oversized or unavailable log tails return an error.

The dark layout uses a sidebar on laptops and wider square foldable viewports, top navigation on narrow phones, a flexible resource grid and scrollable configuration panels. Header breadcrumbs follow Services / service ID / resource ID, with links to parent views; event history adds Events beneath the service. Cluster configuration has its own breadcrumb. The footer shows only the refresh interval. Phone controls have at least 44px targets. Resource tabs and navigation use ordinary hash links, supporting browser history and direct links without another routing dependency.

## Service events

Service detail shows at most one event under “Latest event”, above resources. When more retained events are available, “N more events...” links to `#/services/:serviceId/events`; N counts the remaining events in the fetched history. Event history shows the latest 200 retained events, newest first. Events include timestamp, severity, operation, a safe actionable message, and resource, revision, attempt count and scheduled retry time when available. Retry times describe the schedule when the event was recorded. Event history refreshes independently and remains readable without Git or Docker. Loading, empty and unavailable histories are explicit. Persistence and retention follow [reconciliation events](reconciliation-and-deployments.md#service-events).

Resource Configuration presents grouped runtime, networking, environment, storage/device and limit settings. Live state presents container identity, status, revision, image identity, network addresses/aliases and links to container logs. Each tab keeps its full redacted JSON in a collapsed disclosure below the structured view.

Service event messages are restricted to platform-owned safe messages; raw exceptions and causes remain in operator logs. Secret failures show the missing names, reason, dotenv line when known, and the host file to edit alongside its container path. Unknown host mappings are marked unavailable with guidance to check the control-plane bind mount; a container path is never labeled as a verified host path. Values and file contents remain hidden. See [secret diagnostics](configuration.md#environment-variables-and-secrets). These safe messages and structured details are the only persisted errors exposed by the management API. `PaasUiService` reads events through an injected service-event store and verifies that the service is configured before reading its history.

## API and layers

Inspection endpoints are `GET` (also supporting `HEAD`) under `/api/ui`. Responses use `Cache-Control: no-store`; unknown items return 404 and unavailable data 503. The API router independently verifies configured sessions and returns 401 for missing or invalid sessions on requests that reach it directly; external requests through authenticated management ingress redirect to login first. Unsupported methods are rejected. Unknown API paths never fall back to the SPA.

| Endpoint                                                                  | Result                                                                |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `/cluster`                                                                | Cluster identity, redacted configuration, revision and field metadata |
| `/services`                                                               | Configured services with deployment summaries                         |
| `/services/:serviceId`                                                    | Service source, descriptor status/revision and resources              |
| `/services/:serviceId/events`                                             | Latest 200 safe service events, newest first                          |
| `/services/:serviceId/resources/:resourceId`                              | Resource configuration and live container snapshots                   |
| `/services/:serviceId/resources/:resourceId/containers/:containerId/logs` | Bounded, redacted log tail for an owned resource container            |

`PUT /api/ui/cluster/config` accepts `{ revision, changes: [{ path, value }] }` with 1–128 edits. Paths must match editable fields returned by `/cluster`; `services` replaces the service-source mapping as one field. The endpoint requires the existing session when auth is enabled, an `Origin` matching the configured management origin, `X-Paas-Config: 1`, and `Content-Type: application/json`. It rejects malformed requests or invalid edits with 400, cross-origin/missing-header requests with 403, stale revisions with 409, bodies above 64 KiB with 413, and other content types with 415. Persistence failures return a sanitized 503. Success returns a redacted snapshot with the new revision and fields. There is no CORS opt-in. Unauthenticated local development uses the same origin and JSON requirements.

`frontend/paas-ui-router.ts` owns HTTP adaptation and session verification. `PaasUiService` aggregates injected Git, Docker and reconciliation-state interfaces and delegates platform edits and redaction to `PaasConfig`. It serializes UI Git reads in a separate `_paas/ui-git/` cache, avoiding interference with deployment reconciliation. Docker services enforce cluster/service ownership before reading logs; the UI service additionally verifies resource membership. Shared response types live in `@homelab-paas/shared-contracts`.

Frontend `pages/` compose reusable `components/`; `hooks/` own navigation and fetching. The Docker image builds and includes the Vite output; the existing static frontend service serves it. Configuration editing does not add deployment controls or expand the [runtime's supported resource capabilities](configuration.md#implemented-deployment-mvp).
